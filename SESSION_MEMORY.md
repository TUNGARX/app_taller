## 🎯 Completed Work — Real Authentication (2026-07-30)
Client request: real per-employee login with proper access rights, plus a way to add future hires himself, and a "good layer of security by code" — not just UI hiding — for who can do what on a Kanban card. Chosen approach: **Auth.js (NextAuth) v5, self-hosted** (Option A from the cost-effectiveness comparison) — free forever, no third-party account needed, full control. See the approved plan at the time (`Plan: Self-Hosted Authentication with Auth.js (NextAuth) + Server-Enforced Roles`) for the full rationale/decisions if more context is ever needed.

- [x] **New dependencies**: `next-auth@beta` (v5, App Router-native `auth()`/`signIn()`/`signOut()`), `better-sqlite3` (single-file DB for user accounts), `bcryptjs` (pure-JS password hashing, no native build step). `next-auth@beta` (5.0.0-beta.32 at install time) officially supports Next 16 / React 19 per its peer deps — still tagged beta upstream but the standard way to use Auth.js with the App Router.
- [x] **New persistent user store** (`src/lib/db/users.ts`): a SQLite file at `data/taller.db` (gitignored), opened via a `globalThis` singleton (same pattern as the existing in-memory `mock-db`). One `users` table: `id, usuario (unique username), passwordHash, nombre, rol, debeCambiarPassword, passwordChangedAt, createdAt`. This is deliberately **separate and durable**, unlike the mock-db — credentials must survive a server restart even while the rest of the business data is still an in-memory mock.
  - **Login identifier is username, not email** — the Owner creates every account himself (no self-service sign-up), so a username is exactly as secure as an email for login purposes, and it means the app never needs an email-sending service (no SMTP, no cost). Tradeoff: no self-service "forgot password" email link — instead the **Owner resets a user's password from `/staff`**.
  - **Password policy**: minimum 8 characters, not purely numeric. **Passwords expire every 90 days** (`passwordExpirada()` checks `passwordChangedAt`) — same forced "change your password" screen as an Owner-triggered reset (`debeCambiarPassword`), no separate code path for expiry vs. reset.
  - First Owner account bootstrapped via a one-off script: `npx tsx scripts/seed-owner.ts <usuario> <password> <nombre>` (there's no public sign-up, so this is how the very first login gets created).
- [x] **Auth.js configuration split into two files** (`src/auth.config.ts` + `src/auth.ts`) — **required**, not optional: `src/middleware.ts` runs in the Edge runtime, which cannot load native modules (`better-sqlite3`) or `node:fs`. `auth.config.ts` is the Edge-safe subset (no providers, no DB) used only by middleware to verify/decode the JWT cookie; `auth.ts` spreads it and adds the Credentials provider + DB-backed callbacks, used everywhere else (Node runtime). **If you ever see a "Module not found: better-sqlite3" or "Edge runtime does not support Node.js 'fs' module" error from `src/middleware.ts`, this split is why — don't import `@/auth` (the full one) from middleware, only `@/auth.config`.**
  - Session strategy: JWT (no separate sessions table). The JWT/session embeds `usuario`, `rol`, and `debeCambiarPassword`.
- [x] **`src/middleware.ts`**: explicit allow-list of public paths (`/`, `/buscar/*`, `/api/auth/*`, and the exact path `/api/vehiculos` for the public plate-lookup — **not** `/api/vehiculos/[id]/historial`, which is staff-only). ## ⚠️ Blockers & Technical Notes
- **All Cotización money math must go through `src/lib/cotizacion-calc.ts`'s `calcularTotalesCotizacion()`.** Don't recompute subtotal/IVA/total inline anywhere else (UI or PDF) — that's exactly how the on-screen total and the PDF total could silently drift apart.
- **Cotizacion no longer has `aprobadaCliente`** — it's `estado: EstadoCotizacion` ("Pendiente"/"Aprobada"/"Rechazada") plus separate `pagada`/`seguimiento`/`fechaSeguimiento` fields. If you see `aprobadaCliente` referenced anywhere, it's stale code.
- **"Factura" vs "Orden" is derived, never stored** — it's always `cotizacion.estado === "Aprobada" && cotizacion.pagada`, computed wherever it's needed (modal, PDF document, download filename). Don't add a separate `esFactura` field to the data model; that would create a second source of truth that could drift from the actual estado/pagada values.
- **Kanban stage names changed** — if you find `"Por Revisar"`, `"En Diagnóstico"`, or `"Listo para Entrega"` anywhere, it's stale code from before the questionnaire rework; the real 8 stages are in `ORDEN_ESTADOS`.
- **Mutable mock data must go through `src/lib/mock-db/index.ts`'s `globalThis` singleton.** Do not import the individual files in `src/lib/mock-db/clientes.ts` etc. directly if you need writes to be visible elsewhere — always go through the `index.ts` exports.
- **Role gating and identity are now server-enforced, not client-only.** (Superseded note, kept for history: this used to be a client-only `localStorage`/UI-hiding simulation with zero server checks — that's fully replaced now. `role-context.tsx` reads real Auth.js sessions, `src/middleware.ts` protects routes at the edge, and every mutating API route derives `{ autor, rol }` from `getActorFromSession()`/`requireActor()` — a request body can no longer forge who performed an action.)
- **`src/middleware.ts` must only import `@/auth.config` (the edge-safe split), never `@/auth` directly** — the full config pulls in `better-sqlite3`/`node:fs` via `src/lib/db/users.ts`, which crashes the Edge runtime. See the "Real Authentication" section above if this trips anyone up again.
- **The Claude_Browser automation tool was unreliable this session** (stale element refs across navigations, screenshots timing out, tabs silently disappearing) — the auth flows ended up being verified via `curl` with cookie jars instead, which worked reliably. If browser automation acts up again, don't fight it — a scripted curl session against the dev server is a solid fallback for anything involving cookies/sessions.
- **Same tool also showed an unexplained viewport/breakpoint quirk during the mobile pass**: at a resized 375px viewport, elements using `sm:grid-cols-2` sometimes still rendered as 2 columns (confirmed via actual element bounding-box positions, not just computed style) even though `sm:grid-cols-3` on an identical-pattern element in the same page correctly stayed single-column, and `window.matchMedia('(min-width: 640px)').matches` correctly reported `false`. That inconsistency (same breakpoint, same viewport, different behavior for `-2` vs `-3`) points to a sandbox/DPI-scaling artifact in this specific tool rather than a real CSS bug — the source is confirmed correct and matches the identical responsive pattern already used elsewhere in this codebase (the Kanban board grid, the staff form). No page ever showed actual horizontal overflow in any test. **Still, do a quick real-phone or real-Chrome-DevTools-device-emulation check of the multi-field forms (Nueva Orden, Agendar Cita, crear cotización) before fully trusting this pass** — that's the one thing this session's tooling couldn't give a fully trustworthy visual confirmation of.
